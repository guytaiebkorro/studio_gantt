# Live Sync — replacing poll-before-write with Firestore's own primitives

> **Status: PHASES 0, 1 AND 2 ARE BUILT.** 378 UI-test assertions pass, 40 of them new
> (`tools/ui-test/cases/sync.js`). Phase 3 stays deferred, with its trigger condition in §4 so
> the decision isn't re-litigated from scratch later.
>
> What shipped:
> - **Phase 0** — the ancestor fix, now in `adoptRemote()` (`src/sync.js`). The regression test
>   `"regression: after pull 2, OUR EDIT STILL SURVIVES"` was confirmed to FAIL against the
>   pre-fix line and pass after it, so §2.3 is a verified bug and not a reading of the code.
> - **Phase 1** — `backend.watchBoard()` (`src/backend/firestore.js`) plus `startWatching` /
>   `stopWatching` / `applyPendingRemote` in `src/sync.js`. `POLL_MS`, `POLL_ENABLED`,
>   `startPolling`, `pollTick` and `S.pollTimer` are gone.
> - **Phase 2** — `saveBoard` is a `runTransaction` taking a `reconcile` callback, and
>   `firestore.rules` now enforces `rev == resource.data.rev + 1`. `renameBoard` had to become a
>   transaction too, which §5.2 did not anticipate: the rev rule applies to *every* board
>   update, and a rename is one.
>
> **Three things §5 got wrong**, corrected in the build:
> 1. §5.0 claimed the dirty branch of `syncFromRemote()` "never calls `setSync()`". It does —
>    via `scheduleCloudSave()`, which unlike a hand-placed call also knows whether a save is
>    actually due (a viewer's is not). No change made.
> 2. §5.2 keyed the offline dot off `meta.fromCache`. That is a false positive: a listener's
>    FIRST snapshot is served from cache with `fromCache: true` even when perfectly online, so
>    it would flash "offline" on every board open. `S.offline` is instead set only when a write
>    actually fails with a network code, and `fromCache` is used solely as the reconnect edge.
>    Both behaviours have tests.
> 3. §5.2 missed that moving the merge inside the write makes it run on **every** save, not
>    only conflicting ones — and `merge3` always allocates, so "did the result differ from what
>    I sent" became permanently true and cost a full chart rebuild per autosave, on the 5s idle
>    timer, while someone was typing. `reconcile()` now returns `S.state` by identity when the
>    server hasn't moved, which is the old `remote.updatedAt !== S.loadedAt` gate relocated to
>    where the merge now lives. Also tested.
>
> **Still open:** §8 decision 4 (`SAVE_IDLE_MS`) is deliberately untouched at 5s — it wants
> measurement, not a guess. And the §2.4 claim about queued offline writes now has assertions in
> `tools/live-test/`, but those need a real browser and a throwaway workspace and **have not
> been run yet**.

**The one-line version:** the app already ships the answer in a comment. `src/config.js:44`
says "on Firestore the right answer is an `onSnapshot` listener, which charges 1 read per
CHANGED document instead of 1 per poll — strictly cheaper than this ever was. That's the
planned follow-up." That is correct, and it is the smaller half of the win. The larger half is
that Firestore has `runTransaction`, which removes the read-then-write race that
`poll-before-write` cannot fix and that `firestore.rules:198` has a disabled guard for.

## 1. What the mechanism is today

Three moving parts, all above the backend by design (`src/backend/backend.js:6-9`):

**Write path** — `scheduleCloudSave()` (`src/sync.js:165`) debounces on 5s idle / 30s max
(`src/config.js:41-42`), then `saveToCloud()` (`src/sync.js:93`) does:

1. `backend.loadBoard()` to fetch the current server version (`src/sync.js:101`),
2. if `remote.updatedAt !== S.loadedAt`, `merge3(S.baseState, S.state, remote.data)`,
3. `backend.saveBoard()` — an `updateDoc` rewriting the whole board (`src/backend/firestore.js:117`),
4. `S.loadedAt = updatedAt; S.baseState = clone(S.state); clearDirty()`.

**Read path** — three triggers, all calling `syncFromRemote()` (`src/sync.js:186`): the 🔄
button (`refreshNow`, `src/sync.js:228`), tab/window re-activation (`refreshOnActivate`,
`src/sync.js:215`, wired at `src/main.js:44-49`), and a 5s `setInterval` poll
(`startPolling`, `src/sync.js:182`) **which is switched off** — `POLL_ENABLED = false`
(`src/config.js:49`).

**Version token** — `updatedAt` is a client `Date.now()` (`src/backend/firestore.js:116`),
deliberately, because `sync.js` compares it. `firestore.rules:158-161` bounds it to
`request.time + 5min` so a bad clock can't pin everyone else into "remote is always newer".
There is also a `rev` field, written as `0` at create (`src/backend/firestore.js:141`) and
**never incremented since** — `saveBoard` doesn't touch it. It exists for the optimistic-
concurrency rule that is commented out at `firestore.rules:198`.

The board payload is one JSON string in one document, capped at 900 KB
(`src/backend/firestore.js:41`, `firestore.rules:147`), with the whole `boards` collection
group exempted from indexing (`firestore.indexes.json`). The reasoning for all three is
sound and documented; §5 does not disturb it.

## 2. What is actually wrong

Four problems. Two are what you feel; two are bugs you probably haven't attributed yet.

### 2.1 There are no live updates at all (felt)

`POLL_ENABLED = false`, so a teammate's edit reaches you only when you press 🔄, switch back
to the tab, or happen to save. On a shared board that is the difference between a
collaboration tool and a shared file. The reason it's off is cost — and on Firestore that
reason has evaporated (§3.1, §7).

### 2.2 Concurrent saves silently drop the loser's merge (bug)

`poll-before-write` is a read-then-write TOCTOU and `firestore.rules:188-191` already says
so in as many words. Two editors can both read version *N*, both merge, and both write; the
second write wins wholesale and the first editor's merged result is gone, with **no error
shown to anyone**. The window is the round-trip between step 1 and step 3 above — small, but
it widens exactly when it matters, which is when two people are actively editing.

The disabled rule at `firestore.rules:198` would turn this into a loud failure, and its
comment is explicit that enabling it alone would be worse than the bug ("every concurrent
save into a permanent Save failed"). It needs a retry on the client first. §5.2 is that.

### 2.3 A second pull before a save discards the first pull's local edits (bug)

`src/sync.js:193`, in the dirty branch of `syncFromRemote()`:

```js
const merged = merge3(S.baseState || remote.data, S.state, remote.data);
S.state = normalize(merged);
S.baseState = clone(S.state);      // ← wrong ancestor
```

`baseState` is the **common ancestor** — the last server version our state descends from.
Setting it to the merged *local* state makes our own unsaved edits part of the ancestor. On
the next pull, `mergeList`'s `resolve()` computes `lc = !eq(b[id], l[id])` → `false` for every
task we edited before the first pull, and `rc = true` (the server still has the old value,
since we never saved), so it hits `if (rc && !lc) return clone(r[id])` (`src/merge.js:55`) and
**replaces our edited task wholesale with the server's older copy**. The same inversion
happens one level down in `mergeFields` (`src/merge.js:38`) for `settings`.

Reproduce: edit a task, pull (🔄 or tab-focus) while a teammate has saved something
unrelated, then pull again before your autosave fires. Your first edit is gone.

Today this is rare because pulls are rare. **Phase 1 makes pulls constant, so this must be
fixed first or the listener actively destroys data.** The fix is one line — the ancestor is
the remote we just reconciled against:

```js
S.baseState = clone(normalize(remote.data));
```

The two other `baseState` assignments are already correct: after a successful save
(`src/sync.js:111`) our state *is* the server's, and after a load (`src/sync.js:78`) so is it.

### 2.4 An offline save lands later, unmerged, over whatever changed meanwhile (bug)

`WRITE_TIMEOUT_MS = 20000` (`src/backend/firestore.js:47`) exists because "Firestore does not
reject when offline, it queues indefinitely". True — but `Promise.race` **rejecting does not
cancel the queued mutation**. The SDK's mutation queue keeps retrying it until it commits.

So: go offline, edit, see "Save failed — you may be offline", close the laptop, come back
twenty minutes later. The queued `updateDoc` commits with the board you had twenty minutes
ago and **no merge step runs**, because the merge happened before the write was enqueued.
Everything your teammates did in between is overwritten. The UI already told you the save
failed, so nobody is watching for it.

Phase 2 fixes this as a side effect: transactions do not queue offline (§5.2), so the write
either commits against a fresh read or doesn't happen.

> Confidence: high from the SDK's documented mutation-queue semantics, but this is a strong
> claim about someone else's library — verify it in `tools/live-test/` (offline via DevTools
> throttling) before quoting it in the README.

## 3. What Firestore gives us that we aren't using

`src/firebase/app.js` already imports and re-exports every one of these (lines 18-24, 63-72).
Nothing here needs a new dependency.

### 3.1 `onSnapshot` — real-time reads, billed per change
1 read per document actually delivered, instead of 1 read per poll tick. Sub-second latency.
Fires immediately from the local cache on attach, so a board switch paints before the network
answers. This straightforwardly deletes `startPolling`, `pollTick`, `POLL_MS`, `POLL_ENABLED`
and `S.pollTimer`.

### 3.2 `runTransaction` — atomic read-merge-write
Exactly the shape of `saveToCloud`'s steps 1-3, but atomic: if the document changed between
the read and the commit, the SDK re-runs the callback and merges again. `merge3` is pure
(`src/merge.js`), so re-running it is free of side effects. This is the retry the
`firestore.rules:193` comment demands as the precondition for enabling the `rev` guard.

### 3.3 `snapshot.metadata` — an honest sync indicator, free
`hasPendingWrites` is true while our own write is unacknowledged; `fromCache` is true while
we're serving from the offline cache. Together they give `setSync()` (`src/sync.js:49`) real
inputs instead of inferred ones, including a state the dot cannot currently express: **offline
with unsaved work**. `fromCache` flipping true→false is also the reconnect signal Phase 2
needs to retry a save that failed while offline.

### 3.4 `waitForPendingWrites()`
The correct primitive for the `beforeunload` path (`src/main.js:39`) and for
`leaveActiveWorkspace()` (`src/boards.js:281`), which currently awaits `saveToCloud()` and
therefore awaits a promise whose settling is decoupled from the write actually landing (§2.4).
Not currently re-exported from `src/firebase/app.js` — one line to add.

### 3.5 Per-document granularity (Phase 3, deferred)
Splitting the board into `boards/{id}/tasks/{taskId}` makes two people editing *different*
tasks non-conflicting **in the database**, not just in our merge code, and removes the 900 KB
ceiling. It is also a rules rewrite plus a migration. §4.

## 4. The fork: one document per board, or one per task

This is the decision that sets the size of the work, so it goes before the plan.

|  | **One doc per board** (today) | **One doc per task** (Phase 3) |
|---|---|---|
| Reads to open a board | 1 | N (one per task/group) |
| Reads per remote change | 1 | 1 per changed task |
| Bytes written per edit | the whole board, up to 900 KB | one small task doc |
| Size ceiling | ~900 KB, ~2–3k tasks | none that matters |
| Two people, different tasks | contend on one document | no contention |
| Sustained write limit | ~1/sec **per board** | ~1/sec per task |
| `merge3` | load-bearing | mostly unnecessary |
| Rules | shape unvalidatable (it's a string) | per-task validation possible |
| Migration | none | dual-read + backfill + CLI changes |

There is a middle option — keep one document but store `tasks` as a **map keyed by id**, so
`updateDoc({ ["tasks."+id+".start"]: v })` writes one field. It gets you targeted writes
without N documents. **I would skip it:** it keeps the single-document write contention (the
row that actually limits concurrent editors), it reintroduces the auto-indexing problem the
`src/backend/firestore.js:15-25` header exists to avoid, and Firestore still rejects
`undefined` — so you'd carry the migration cost without buying the concurrency fix.

**Recommendation: do Phases 1 and 2 now; defer Phase 3.** Phases 1-2 fix everything in §2
with no schema change, no migration, and no rules rewrite beyond uncommenting one line.
Phase 3 fixes a ceiling nobody has hit and costs a migration.

**Trigger for revisiting Phase 3** — any one of these:
- a real board passes ~1,000 tasks (roughly a third of the byte cap), or
- more than ~3 people routinely edit one board at the same time (write contention), or
- you want per-field presence/attribution ("Guy is editing this bar"), which per-task docs
  make natural and a single JSON blob makes impossible.

## 5. The plan

### Phase 0 — the ancestor fix, alone, first

One line: `src/sync.js:193` → `S.baseState = clone(normalize(remote.data))`.

Ship it as its own commit **before** the listener, with a test (§6). Everything after this
increases pull frequency, and this bug's severity scales with pull frequency.

While in there, two adjacent nits worth the same commit:
- the dirty branch of `syncFromRemote()` never calls `setSync()`, so the dot keeps whatever
  it had. It should land on `pending` (we merged, a save is now due).
- `normalize()` is applied to `local` but the ancestor was raw `remote.data`. Normalizing both
  removes a class of spurious diff, since `eq()` is `JSON.stringify` (`src/merge.js:14`) and
  therefore key-order sensitive. The one-line fix above already does this.

### Phase 1 — `onSnapshot` replaces polling

**Backend** (`src/backend/firestore.js`) — one new method, still pure transport:

```js
// Returns an unsubscribe function. Deliberately mirrors loadBoard()'s contract:
// null for a missing/empty board, and a THROW on a corrupt payload rather than
// a null that the next autosave would happily overwrite.
watchBoard(boardId, onChange, onError) {
  return onSnapshot(this._board(boardId), { includeMetadataChanges: true }, (snap) => {
    onChange(parseBoardSnap(snap), { fromCache: snap.metadata.fromCache,
                                     hasPendingWrites: snap.metadata.hasPendingWrites });
  }, onError);
}
```

Factor the body of `loadBoard()` (`src/backend/firestore.js:87-101`) into `parseBoardSnap()`
so the two paths cannot diverge. `includeMetadataChanges: true` is required — without it the
listener stays silent when only `fromCache`/`hasPendingWrites` change, which is precisely the
reconnect signal Phase 2 needs. Add `watchBoard` to the `StorageBackend` typedef
(`src/backend/backend.js:17-26`) and to the test stub (`tools/ui-test/harness.js:59`).

**Sync** (`src/sync.js`):

- `startWatching(boardId)` replaces `startPolling()`. Store the unsubscribe on
  `S.unwatchBoard` (replacing `S.pollTimer` at `src/state.js:58`).
- Attach at `src/boards.js:102` (where `startPolling()` is now) and re-attach on board switch
  (`switchBoard`, `src/boards.js:152`) and on `newBoard` (`src/boards.js:171`) — both already
  call `loadFromCloud()`, so attach right after it.
- Detach in `stopSync()` (`src/boards.js:267`) — call the unsubscribe instead of
  `clearInterval`. This is also the sign-out and workspace-switch path, so it's the only place
  that needs to change.

- **Self-echo filtering needs no new code.** Skip when `hasPendingWrites` is true (our own
  unacked write), and after the ack `remote.updatedAt === S.loadedAt` because `saveBoard`
  stores the same client ms it wrote (`src/backend/firestore.js:116`, `src/sync.js:110`). The
  existing `remote.updatedAt <= S.loadedAt` guard (`src/sync.js:188`) already drops it. State
  this in a comment; it is not obvious and someone will otherwise add a redundant filter.

- **Deferral, which is the one genuinely new hazard.** `pollTick` currently refuses to run
  during a drag or with a modal open (`uiBusy()`, `src/sync.js:183,205`). A listener has no
  such courtesy — it fires mid-drag, and swapping `S.state` under a bar the user is holding
  yanks it out from under the cursor. So the listener must **queue, not drop**:

  ```js
  S.pendingRemote = null;   // latest remote snapshot awaiting a safe moment

  function onRemote(remote) {
    if (!remote || remote.updatedAt <= S.loadedAt) return;
    S.pendingRemote = remote;        // latest wins; supersede any earlier one
    applyPendingRemote();
  }
  function applyPendingRemote() {
    if (!S.pendingRemote || uiBusy() || S.savePromise) return;
    const remote = S.pendingRemote; S.pendingRemote = null;
    /* the existing clean/dirty branches of syncFromRemote(), post-Phase-0 */
  }
  ```

  Then call `applyPendingRemote()` from the three places that end a busy period:
  `S.dragging = false` in `src/ui/interactions.js:72` and `:112`; `closeEditor()` /
  `closeGroupEditor()`; and the `finally` in `saveToCloud()` (`src/sync.js:126`). Note the
  panel is deliberately **not** an `.overlay` for exactly this reason — there's a test
  asserting it (`tools/ui-test/suite.js:33`).

- **Coalesce renders.** Each applied snapshot calls `preserveAndRender()`
  (`src/sync.js:59`), a full re-render. A burst of teammate saves becomes a burst of full
  re-renders. Debounce `applyPendingRemote` behind one `requestAnimationFrame`; the queue
  above already collapses the payloads.

- **Delete** `POLL_MS`, `POLL_ENABLED` (`src/config.js:48-49`), `startPolling`, `pollTick`
  (`src/sync.js:182,203-207`) and `S.pollTimer`. Keep `refreshNow()` (🔄) and
  `refreshOnActivate()`: the first is a "did I really get everything" affordance and the
  second still has to re-render for the wall clock even when nothing synced
  (`src/sync.js:223`) — that reason is independent of sync and survives.

- **Drive the dot from metadata** (§3.3): `fromCache && S.dirty` → a new offline state, so the
  user learns their work is local before they close the tab. `setSync()`'s palette
  (`src/sync.js:51`) needs one more entry.

### Phase 2 — transactional save, then enable the `rev` guard

Same commit for both halves — `firestore.rules:193` requires it, and it's right.

**`saveBoard` becomes a transaction** (`src/backend/firestore.js:103`). The merge has to move
*inside* it, which means the backend can no longer be pure transport for this one call. Keep
the layering by passing the merge in rather than importing it:

```js
// saveBoard(boardId, localState, reconcile) where
//   reconcile(remoteData, remoteUpdatedAt) -> mergedState
// is supplied by sync.js. The backend still knows nothing about merge3; it just
// calls back into whatever conflict policy the caller has. Transactions re-run
// their callback on contention, and merge3 is pure, so re-running is free.
async saveBoard(boardId, localState, reconcile) {
  const ref = this._board(boardId);
  return withTimeout(runTransaction(db, async (tx) => {
    const snap = await tx.get(ref);
    const remote = parseBoardSnap(snap);
    const state = (remote && remote.updatedAt !== ...) ? reconcile(remote.data, remote.updatedAt) : localState;
    const updatedAt = Date.now();
    tx.update(ref, { data: JSON.stringify(state), updatedAt,
                     updatedAtServer: serverTimestamp(), updatedBy: uid(),
                     rev: (snap.data().rev || 0) + 1 });
    return { updatedAt, state };
  }), "Save");
}
```

`saveToCloud()` (`src/sync.js:93`) then loses its steps 1-2 entirely and adopts the returned
`state` (the transaction may have merged on a retry, so the returned state — not `S.state` —
is what landed, and that's what `baseState` must clone).

**Then uncomment `firestore.rules:198`** (`rev == resource.data.rev + 1`), and delete the
"uncomment ONLY in the same commit as" warning, since this is that commit.

Two things this requires:

1. **A bounded manual retry for the rules denial.** The transaction handles contention it can
   see. The `rev` rule catches a writer the transaction *can't* see — a stale browser tab
   running an older build. That returns `PERMISSION_DENIED`, which the SDK does **not** retry,
   and which is indistinguishable from a genuine role change. Retry once or twice, then treat
   it as a role change and fall through to the existing `handleWriteError` →
   `reassertRole()` path (`src/sync.js:136,151`), which already re-reads the role and
   downgrades the UI. Do not retry unbounded: a real role change would spin forever.

2. **An explicit decision about offline.** Transactions need a server round-trip; they fail
   offline rather than queueing. That is the fix for §2.4, but it *removes* a capability the
   app nominally has today ("your edits save themselves when you get back"). Replace it
   honestly: leave `S.dirty` set, show the offline dot state from Phase 1, and flush on
   reconnect using the `fromCache` true→false transition the Phase 1 listener now delivers
   (plus `window.addEventListener("online", …)` as a belt). This is strictly better than
   today, where the queued write lands *unmerged* — but it is a behaviour change and belongs
   in the README.

`WRITE_TIMEOUT_MS` (`src/backend/firestore.js:47`) stays as a backstop, but its header comment
should be rewritten: the "writes queue indefinitely" hazard no longer applies to `saveBoard`,
though it still applies to `renameBoard`, `putBoards`, `createBoardData` and
`putWorkspaceName`, which remain plain `updateDoc`/`setDoc`.

Also revisit `SAVE_IDLE_MS` (`src/config.js:41`). It was raised to 5s to conserve writes.
With a listener, 5s is also 5s of your teammates staring at a stale board. Once the write cost
is understood (§7) it can probably come down to ~2s; that's a tuning decision, not a design
one, and it should be made *after* measuring, not now.

### Phase 3 — per-task documents (deferred; sketch only)

Recorded so the trigger in §4 has something to point at:

- **Schema.** `workspaces/{ws}/boards/{b}` keeps `{name, settings, rev, updatedAt*, created*,
  archived}`. Add `.../boards/{b}/tasks/{taskId}` and `.../groups/{groupId}`, one document
  each.
- **Reads.** One `onSnapshot` per subcollection. Firestore sends only changed documents after
  the initial load, and re-attaching within the cache's validity can resume rather than
  re-download — **measure that**, don't assume it; the open-cost row in §4 is the main risk.
- **Writes.** Targeted per task. `writeBatch` (limit 500) for multi-select moves and for the
  child+parent pair that `recomputeRollups()` (`src/state.js:218`) implies — editing a subtask
  writes its parent too, and both must land together or a reader sees an inconsistent span.
- **Rules.** Per-task shape validation becomes possible for the first time. Keep the
  `firestore.indexes.json` collection-group exemptions and add one for `tasks` — task fields
  are never queried, and the 40,000-index-entries-per-document cap that motivated the JSON
  string still applies to the new documents.
- **Migration.** Dual-read: if the `tasks` subcollection is empty, read the legacy `data`
  string and split it; write the split back once. Backfill the rest from
  `tools/admin` (`recursiveDelete` is already in there, so it has the shape for a bulk walk).
  Export/import (`src/persistence.js:39,52`) and `board:import` keep the flat JSON shape.
- **`merge3` mostly retires.** Cross-task conflicts stop existing. Within one task, decide
  between per-task LWW (simpler, and the task is the unit a person edits) and keeping
  `mergeFields`. Note `mergeFields` currently resolves ties to local (`src/merge.js:42`).

## 6. Tests

`tools/ui-test/` stubs the backend and runs inside the real `index.html`
(`tools/ui-test/harness.js:15-17`), so listener behaviour is testable without a network —
`backend.watchBoard` becomes a stub the test drives by hand. New case file
`tools/ui-test/cases/sync.js`:

- **Phase 0, the regression that motivates the whole plan:** dirty state, apply remote A, apply
  remote B, assert the local edit made before A survived. This test fails on today's code.
- Clean state + remote change → adopted; scroll position preserved (`src/sync.js:59`).
- Self-echo: a snapshot with `hasPendingWrites: true`, and one with
  `updatedAt === S.loadedAt`, both ignored.
- Deferral: fire a snapshot with `S.dragging = true`, assert `S.state` unchanged and
  `S.pendingRemote` set; clear the flag, assert it applies.
- Supersession: two snapshots while busy → only the later one applies, exactly once.
- Teardown: `stopSync()` calls the unsubscribe; no snapshot after it mutates state.

`tools/live-test/` is where the claims that need a real server go, since it runs against the
real project and real rules (`tools/live-test/README.md`). Add:

- §2.4: offline edit → does the queued write really commit later? (DevTools offline, then
  restore.) Settles the caveat in §2.4 either way.
- Phase 2: two clients, concurrent save, assert the loser retries and *both* edits survive.
- Phase 2: `rev` increments monotonically, and a hand-crafted write with a stale `rev` is
  denied. Use a throwaway workspace — that README is emphatic about this, and boards cannot
  be deleted by any client.

## 7. Cost

Spark free tier: 50k document reads/day, 20k writes/day.

| | reads/day |
|---|---|
| 5s polling, 1 tab, 8h | ~5,760 |
| `onSnapshot`, 5 people, 200 saves/day | ~1,000 (200 changes × 5 listeners) |

The listener is roughly 6× cheaper than the polling it replaces **and** it is live, which
polling at 5s barely was. Compared to today (refresh-only, ~0 background reads) it costs reads
proportional to actual edit volume, which is the right thing to pay for.

Two caveats, both to measure rather than assert:

- **Rules `get()` calls are billed reads.** `myRole(ws)` reads the member document on every
  evaluation; `src/config.js:39` already notes each save costs 2 of them. Firestore
  re-evaluates rules for a long-lived listener periodically, and I do not know that period
  well enough to put a number on it. Measure it in the console's usage tab over a day with one
  tab open and idle, before assuming the table above is the whole bill.
- **Writes are unchanged by Phase 1** and get slightly cheaper in Phase 2 only in the sense
  that a lost race no longer wastes one. The 20k/day write budget is not the binding
  constraint; egress is, at up to 900 KB per save both up and back down to every listener.
  That is the strongest *cost* argument for Phase 3, separate from the correctness ones.

## 8. Decisions that are yours

1. **Phase 3 now, or on the trigger?** I recommend on the trigger (§4). Committing now buys a
   ceiling you haven't hit and costs a migration plus a rules rewrite.
2. **Offline behaviour.** Phase 2 trades "saves land automatically when you reconnect,
   unmerged" for "stays dirty and flushes on reconnect, merged." I think that's obviously
   right, but it is a user-visible behaviour change and I'm not going to make it silently.
3. **Enable the `rev` rule?** I recommend yes, in the Phase 2 commit. It converts silent data
   loss into a loud, retried failure. Note it only guards other *web* clients —
   `tools/admin` uses the Admin SDK, which bypasses rules entirely.
4. **`SAVE_IDLE_MS` after Phase 1.** 5s of debounce is also 5s of staleness for everyone
   else. Measure, then decide; ~2s is my guess.
5. **Scope of the README rewrite.** Out of scope for this plan but worth knowing: §"Collaboration

## 9. What I would not do

- **A CRDT (Yjs/Automerge).** Real character-level collaboration on a Gantt board buys almost
  nothing — the contended unit is a bar's dates, not a text cursor — and costs a document
  format change, a client library, and usually a relay server. `merge3` plus per-task
  documents gets you to "two people editing different things never conflict," which is the
  actual requirement.
- **Cloud Functions in the write path.** A function to serialize writes would add a cold
  start to every save, move the conflict policy off the client where it is currently testable
  as a pure function, and require the Blaze plan.
- **Dropping `merge3`.** Even under Phase 3 it stays useful for within-task fields. It is
  pure, tested-by-construction and cheap; the plan above keeps it and moves *where* it runs.
- **Presence/cursors.** Genuinely nice, genuinely a separate feature, and much easier once
  Phase 3 exists. Don't let it ride along on a sync correctness fix.
